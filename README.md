# Практическая работа №6 — Синхронизация

**Вариант B**

Цель работы — реализовать синхронизацию потоков с помощью мьютексов, семафоров и условных переменных, проверить инварианты ограниченного буфера и реализовать собственный барьер.

## Что реализовано

### 1. Производитель–потребитель: семафоры + мьютекс

Файл: `producer_consumer_semaphore.py`

Кольцевой буфер имеет размер **5** и реализован вручную, без `queue.Queue`.

Используются:

- `empty = Semaphore(5)` — число свободных ячеек;
- `full = Semaphore(0)` — число заполненных ячеек;
- `mutex = Lock()` — защищает `buffer`, `head`, `tail` и `count`.

В тесте работают **3 производителя** и **2 потребителя**, всего производится **1000 уникальных элементов**.

Алгоритм `put`:

1. `empty.acquire()` — дождаться свободной ячейки;
2. захватить `mutex`;
3. записать элемент в `tail`;
4. сдвинуть `tail` по кольцу и увеличить `count`;
5. освободить `mutex`;
6. `full.release()` — сообщить, что появился элемент.

Алгоритм `get` симметричен: сначала `full.acquire()`, затем чтение под мьютексом и в конце `empty.release()`.

### 2. Производитель–потребитель: мьютекс + Condition

Файл: `producer_consumer_condition.py`

Используются один `Lock` и одна `Condition`, связанная с этим мьютексом.

Производитель ждёт:

```python
while self.count == self.capacity:
    self.changed.wait()
```

Потребитель ждёт:

```python
while self.count == 0:
    self.changed.wait()
```

После изменения состояния вызывается `notify_all()`.

`while` здесь принципиален: поток после пробуждения снова захватывает мьютекс, но к этому моменту другой поток уже мог изменить состояние буфера.

## Проверка корректности

Проверки находятся прямо в коде, а не выполняются «на глаз».

Для каждого запуска проверяется:

- произведено/потреблено ровно 1000 элементов;
- каждый ID от `0` до `999` потреблён ровно один раз;
- нет пропущенных элементов;
- нет неожиданных ID;
- `count` никогда не становится меньше 0;
- `count` никогда не становится больше 5;
- `head` и `tail` всегда остаются внутри кольца;
- максимальный фактический размер буфера не превышает 5.

Нарушения записываются через `logging` в:

- `semaphore_violations.log`;
- `condition_violations.log`.

При корректном запуске файлы не содержат ошибок. В конце выполняется `assert result.ok`.

Пример результата:

```text

Пропущено            : 0
Дубликатов            : 0
Нарушений инвариантов : 0
```

## 3. Барьер на условной переменной

Файл: `barrier_demo.py`

Реализован собственный циклический `ConditionBarrier` для **4 потоков**.

Каждый поток выполняет задачу в **трёх фазах**. После каждой фазы поток вызывает `barrier.wait()` и не может начать следующую фазу, пока остальные три потока не закончат текущую.

Барьер хранит:

- `count` — сколько потоков пришло к барьеру;
- `generation` — номер текущего поколения/фазы.

Последний из четырёх потоков:

1. сбрасывает `count` в 0;
2. увеличивает `generation`;
3. вызывает `notify_all()`.

Остальные ждут в цикле:

```python
while my_generation == self.generation:
    self.condition.wait()
```

После трёх фаз автоматически проверяется:

```python
assert barrier.count == 0
assert barrier.generation == 3
```

## 4. Почему `if` вокруг `wait()` ломается

Ошибочная версия: `lost_wakeup_demo.py`  
Исправленная версия: `condition_while_fixed.py`

В ошибочной версии используется:

```python
if self.item is None:
    self.condition.wait()
```

В исправленной:

```python
while self.item is None:
    self.condition.wait()
```

### Чередование, при котором возникает ошибка

Пусть есть два потребителя `C1`, `C2` и один элемент:

1. `C1` видит пустой буфер и вызывает `wait()`.
2. `C2` тоже видит пустой буфер и вызывает `wait()`.
3. Производитель кладёт один элемент `42` и вызывает `notify_all()`.
4. Просыпаются оба потребителя.
5. `C1` первым получает mutex, забирает `42`, буфер снова пуст.
6. `C2` получает mutex после `C1`.
7. Если использован `if`, `C2` **не проверяет условие повторно** и продолжает работу так, будто элемент существует.
8. В демонстрации фиксируется нарушение: `C2` получил пробуждение, но элемента уже нет.

При `while` шаг 7 другой: `C2` повторно видит `item is None` и снова засыпает до появления следующего элемента.

В литературе это часто точнее называют проблемой повторной проверки предиката после пробуждения (stolen/spurious wakeup). Классическое «потерянное уведомление» также предотвращается тем, что состояние-предикат проверяется под тем же мьютексом, что и `wait/notify`.

## Контрольные вопросы

### 1. Чем семафор со значением 1 отличается от мьютекса на практике?

Оба могут ограничить одновременный доступ одним потоком, но смысл разный.

**Мьютекс** выражает владение критической секцией: поток захватил блокировку и этот же поток обычно должен её освободить. Он предназначен именно для взаимного исключения при работе с общими данными.

**Семафор** — счётчик разрешений. `acquire()` уменьшает число разрешений, `release()` увеличивает. Разрешение может освободить другой поток. Поэтому бинарный семафор можно использовать как ограничитель ресурса или средство сигнализации, но для защиты обычной критической секции логичнее использовать `Lock`.

### 2. Почему условную переменную нельзя использовать без мьютекса?

Условная переменная сама не хранит состояние, например «буфер не пуст». Состояние хранится в обычных переменных программы.

Проверка условия и переход в `wait()` должны быть одной атомарно защищённой последовательностью. Иначе возможна гонка:

1. потребитель проверил, что данных нет;
2. производитель добавил данные и отправил уведомление;
3. потребитель только после этого начал ждать;
4. уведомление уже прошло, поэтому потребитель может ждать бесконечно.

Мьютекс связывает проверку предиката с `wait()`: `Condition.wait()` атомарно освобождает mutex и переводит поток в ожидание, а перед возвратом снова захватывает его.

## Вывод

Семафоры удобно описывают количество свободных и занятых ячеек, а мьютекс защищает само состояние кольцевого буфера. `Condition` позволяет ждать изменения логического условия, но условие необходимо проверять в цикле `while`. Инварианты и unit-тесты подтверждают, что при корректной синхронизации 1000 элементов обрабатываются ровно по одному разу и буфер никогда не выходит за границы `0..5`.
